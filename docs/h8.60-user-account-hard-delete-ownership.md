# H8.60 User Account Hard-delete Ownership Map

## Contract decision

`Pengguna` deletes the selected `MASTER_USER` login credential permanently. For a student-linked account it also deletes only private `MASTER_NOTIFICATION` inbox rows addressed to that account. It deliberately preserves `MASTER_STUDENT` as the canonical historical identity anchor and therefore preserves every `Student_ID`-linked record.

This is separate from `Master Siswa`, which continues to call `StudentService::deleteStudent()`. That lifecycle operation deletes `MASTER_STUDENT` only when its existing invoice and score integrity guards allow it; it never calls the User Management hard-delete method.

The student anchor cannot safely be removed during an account-only deletion: finance, academic, attendance, documents, alumni, and enrollment repositories resolve display and ownership through `MASTER_STUDENT.Student_ID`, and the current Google Sheets schema has no immutable student snapshot or nullable foreign-reference migration.

## Proven ownership matrix

| Entity | Canonical key / relation | Owned by login account? | Hard-delete safe from Pengguna? | Decision and evidence |
|---|---|---:|---:|---|
| `MASTER_USER` | `User_ID` | Yes | Yes | Authentication source in `GoogleSheetsUserProvider`; User Management explicitly owns this row. Delete and verify a fresh `findById()` miss. |
| `MASTER_NOTIFICATION` | `Notification_ID`; recipient `User_ID`, `Recipient_User_ID`, `Recipient_ID`, or account email | Yes | Yes | Private delivery/inbox state has no independent historical identity. Resolve all canonical notification IDs first, hard-delete each ID, then read back. |
| `MASTER_STUDENT` | `Student_ID`; exact `User_ID` link | No: student identity/lifecycle | No | It is the canonical anchor used throughout student, billing, reporting, and alumni services. Preserve the row and exact link, then read back after account deletion. |
| `MASTER_SCORE` (including Ujian Bab) | `Score_ID` -> `Student_ID` | No | No | Academic history. `ScoreService`, reports, and teacher/student workspaces resolve it by `Student_ID`. |
| `MASTER_ATTENDANCE` | `Attendance_ID` -> `Student_ID` | No | No | Academic attendance history. Student and teacher workspaces resolve by `Student_ID`. |
| `MASTER_ATTENDANCE_REQUEST` | `Request_ID` -> `Student_ID` / requester | No | No | Workflow/history; preserve with the student anchor. |
| `FINANCE_INVOICE` | `Invoice_ID` -> `Student_ID` | No | No | Accounting record; `StudentService::deleteStudent()` already blocks deletion when invoices exist. |
| `FINANCE_PAYMENT` | `Payment_ID` -> `Student_ID`, `Invoice_ID` | No | No | Verified payment and reconciliation history is immutable/compensated by finance services. |
| `FINANCE_TRANSACTION` (ledger) | `Transaction_ID` -> finance reference/source | No | No | Ledger history; payment-linked transaction deletion is explicitly rejected by `TransactionService`. |
| Billing views | Derived from invoice/payment by `Student_ID` | No | N/A | No separate owned row; preserved finance rows remain resolvable through the preserved student anchor. |
| `MASTER_DOCUMENT` | `Document_ID`; `Student_ID`, owner/reference fields | No | No | Certificates, academic reports, and finance documents are historical artifacts. |
| `MASTER_ALUMNI` | `Alumni_ID` -> `Student_ID` | No | No | Historical departure registry. `StudentService::isAlumni()` and `AlumniRepository` use `Student_ID`. |
| `MASTER_CLASS_ENROLLMENT` | `Enrollment_ID` -> `Student_ID` | No | No | Student lifecycle/placement relation, not a login credential. |
| Schedules / assignments / assessments | Class/teacher relations; student consumption is indirect | No | No | No authoritative account ownership for a student login. |
| Audit/activity, approvals, workflows | actor/request/reference IDs | No | No | Historical evidence must survive account deletion. No fake actor or replacement ID is created. |

## Coordinated delete plan

1. Resolve the canonical `MASTER_USER.User_ID` server-side and require an exact ID match.
2. Reject self-delete and deletion of the last active Administrator/Master.
3. Resolve the role and every exact `MASTER_STUDENT.User_ID` relationship.
4. Validate that all linked student rows have present, unique canonical `Student_ID` values.
5. Resolve and validate all account-owned notification primary keys.
6. Hard-delete notifications by canonical ID. Each repository hard delete performs a fresh sheet lookup, so prior row shifts cannot stale a later target.
7. Clear/read back notifications and require that no addressed row remains.
8. Hard-delete `MASTER_USER` by canonical `User_ID` and verify it is absent.
9. Clear/read back `MASTER_STUDENT`; require every original student anchor and exact `User_ID` relationship to remain readable.
10. Clear affected caches. No fake Student/User ID, row index, sheet, or column is created.

## Authorization and UI

The `users.destroy` route remains inside the existing `role:ADMINISTRATOR` group. The service independently resolves the target from `MASTER_USER`, rejects a forged/mismatched ID, blocks deletion of the active actor, and blocks deletion of the final active Administrator/Master. The Pengguna confirmation explicitly says the account deletion is permanent while required historical data is retained.
