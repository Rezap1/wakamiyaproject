# H8.26 schema-alignment prerequisite (production read-only audit)

This plan is documentation only. No production Google Sheet was mutated by
H8.26. The application now fails closed before any finance-domain append or
update when one of these columns is absent.

## Required columns

| Sheet | Required fields added/confirmed by application | Current production observation (2026-09-02) | Gate |
| --- | --- | --- | --- |
| `FINANCE_PAYMENT` | `Created_By`, `Updated_By`, `Idempotency_Key`, `Idempotency_Fingerprint`, `Receipt_Number`, `Payment_Type`, `Is_Active` | all seven missing; existing 14-column sheet is otherwise readable | **BLOCKER** |
| `FINANCE_INVOICE` | `Line_Items`, `Created_By`, `Updated_By`, `Is_Active` | all four missing; existing 12-column sheet is readable | **BLOCKER** |
| `FINANCE_TRANSACTION` | `Updated_By` | missing; existing 13-column sheet is readable | **BLOCKER** |
| `MASTER_NOTIFICATION` | `Reference_Type`, `Reference_ID` | both missing; existing 8-column sheet is readable | **BLOCKER** |

`Line_Items` is canonical invoice data: `InvoiceService` computes it before
persistence and uses it for amount/audit reconciliation. `Payment_Type` is
the durable discriminator for a payment with blank `Invoice_ID`; dropping it
would make a fresh read unable to recognize student self-service payments.
The two payment idempotency columns and deterministic payment identity are the
persisted source of truth; Laravel file cache is only an optimization.

## Approved deployment procedure (human-controlled)

1. Freeze finance writes and export a timestamped backup of each affected
   sheet, including headers and all rows.
2. Add the missing columns by exact name (case-sensitive) in the approved
   staging spreadsheet first. Preserve all existing columns and rows; do not
   reorder or delete data.
3. Backfill existing rows with an approved, reviewed data-mapping procedure:
   - legacy payments require a deliberate idempotency/identity decision;
   - invoices require canonical `Line_Items` derived from existing amount only
     where the business owner approves that reconstruction;
   - audit columns must be explicit (`MIGRATION`/known actor), never guessed;
   - notification identity cannot be invented for old reminders, so those rows
     remain non-authoritative for dedupe until reviewed.
4. Run `php tools/h826_forensic_readonly.php` against staging and require zero
   schema blockers, authoritative reads for every sheet, and zero unexplained
   reconciliation anomalies.
5. Obtain finance/data-owner approval, schedule the production schema change,
   apply it through the normal deployment procedure, and rerun the same
   read-only auditor. Only then may the application write gate be reopened.

Until this procedure is completed and independently evidenced, deployment is
not permitted. The code deliberately does not contain an automatic migration
or a compatibility path that silently discards these fields.
