# H8.44 Finance Data Integrity

## Canonical financial state

- `invoice_total`: canonical grand total calculated from validated invoice line items. A legacy invoice without line items uses its validated `Amount`.
- `accepted_paid_amount`: sum of `FINANCE_PAYMENT.Amount_Paid` rows whose canonical status is `Verified`, linked to the invoice, counted once per non-empty `Payment_ID`.
- `remaining_balance`: `max(invoice_total - accepted_paid_amount, 0)` at cent precision.
- `payment_status`: one of `Waiting Verification`, `Need Revision`, `Verified`, `Rejected`, `Cancelled`, or `Reversed`. Only `Verified` reduces an invoice balance.
- `invoice_status`: `Draft` and `Cancelled` remain terminal display states; otherwise the accepted payment aggregate derives `Waiting Payment`, `Partial Paid`, `Paid`, or `OVERDUE`.

`Paid_Amount`, `Remaining_Amount`, and display status are derived values. They are never accepted as authoritative client input and must not replace a read of the payment source when no authoritative payment snapshot is supplied.

## Surface contract

`InvoiceService` produces the canonical invoice state used by Student Billing, invoice detail, invoice PDF, Finance Dashboard, and outstanding reports/exports. Receipt calculations and payment mutation guards use the same `AcceptedPaymentCalculator`.

The Student Billing hero represents outstanding balance, not the sum of original invoice totals.

An invoice-less self-service payment is not silently allocated. When an active invoice exists, Finance must select that invoice during verification. A legacy self-service payment that is already `Verified` can be linked through the explicit Finance reconciliation action; ownership, invoice state, overpayment, ledger identity, and rollback are validated server-side.

## Read-only reconciliation

Run the audit without changing any Google Sheets rows:

```shell
php artisan finance:audit-integrity
php artisan finance:audit-integrity --json
```

The command exits unsuccessfully when it finds duplicate identities, stale stored balances/statuses, overpayment, missing or cross-student relationships, an unallocated verified self-service payment beside an active invoice, orphan payment transactions, ledger mismatches, or an invalid reversal ledger. Remediation remains a separate, explicitly authorized operation.
