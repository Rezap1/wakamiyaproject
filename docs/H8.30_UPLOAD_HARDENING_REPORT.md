# WMS H8.30 — Upload Size & 413 Hardening Report

## Scope

This change set audits the application upload paths and makes their application
limit explicit and consistent. No VPS, PHP-FPM, nginx, Google Sheets, database,
production `.env`, or business rule was changed.

## Findings

- The local PHP runtime reported `upload_max_filesize=40M` and
  `post_max_size=40M`; therefore the observed production 413 cannot be
  attributed to the local runtime settings.
- The application had several inconsistent 2 MB limits for student photos,
  employee photos, company branding, and system-setting files.
- Payment proofs, payroll proofs, and attendance evidence already used a 5 MB
  application limit, but the limit was duplicated as literals.
- Company upload forms advertised SVG even though the server-side allow-list
  rejects SVG. The UI now advertises only the formats actually accepted.

## Application contract

`config/upload.php` is now the single application source for the upload ceiling:

- Laravel validation ceiling: **5120 KB (5 MB)**
- Manual system-setting byte check: **5 MiB**
- Existing MIME allow-lists remain enforced; no executable or SVG allowance was
  added.

All audited image, proof, and evidence validation paths use the centralized
5 MB value. Existing payment/attendance required/optional semantics and storage
flows are unchanged.

## Production edge configuration (manual operator action)

The 413 boundary is outside this repository and must be configured on the
Hostinger web/PHP runtime before deployment. Recommended limits are:

```ini
; PHP-FPM / .user.ini (multipart overhead is accommodated by post_max_size)
upload_max_filesize = 5M
post_max_size = 6M
```

```nginx
client_max_body_size 6M;
```

After changing those server settings, restart/reload the relevant PHP-FPM and
web-server services according to Hostinger's control panel procedure. This
report does not perform that action.

## Verification

The focused upload-limit regression tests verify the centralized 5 MB ceiling
and rejection of oversized image uploads. Full PHPUnit, PHP lint, and the
deployment gate should be run in the normal audited build before any release.

## Verdict

Application-side H8.30 hardening is complete. A production 413 cannot be marked
resolved until the operator confirms the nginx/PHP limits above and performs a
real upload smoke test. No deployment or production data mutation was
performed by this change.
