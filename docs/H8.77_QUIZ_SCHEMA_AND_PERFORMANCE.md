# H8.77 Quiz — schema gate and performance evidence

## Production safety

- Production Quiz sheets created: **NO**.
- Production data modified: **NO**.
- Existing business sheets modified: **NO**.
- Quiz is isolated from `MASTER_SCORE`, Finance, Attendance, Payroll, and existing Academic Score.

## Proposed Google Sheets schema

Header order is enforced exactly by each repository's `expectedHeaders` contract. A mismatch fails closed before reads/writes.

### `QUIZ` — 14-day cleanup data

Business ID: `Quiz_ID`. Teacher owns the row; `Class_ID` is revalidated through active `MASTER_SCHEDULE`.

```text
Quiz_ID, Teacher_ID, Class_ID, Title, Start_At, End_At, Duration_Minutes, Status, Created_At, Updated_At, Created_By, Updated_By
```

Relationship: `Teacher_ID -> MASTER_TEACHER`, `Class_ID -> MASTER_CLASS`. Deleted only after the quiz has expired, the global period containing `End_At` is closed, every attempt deadline and result review window has elapsed, and result summaries are finalized.

### `QUIZ_QUESTION` — 14-day cleanup data including secret answer keys

Business ID: `Question_ID`.

```text
Question_ID, Quiz_ID, Question_Text, Option_A, Option_B, Option_C, Option_D, Correct_Option, Point, Sort_Order, Created_At, Updated_At
```

Relationship: `Quiz_ID -> QUIZ`. `Correct_Option` never enters a student response. Rows are physically deleted with eligible quiz content.

### `QUIZ_ATTEMPT` — disposable execution and 4-minute review data

Business ID: deterministic `Attempt_ID = hash(Quiz_ID|Student_ID)`.

```text
Attempt_ID, Quiz_ID, Student_ID, Started_At, Deadline_At, Status, Submitted_Answers_JSON, Submitted_At, Created_At, Updated_At
```

Relationship: `Quiz_ID -> QUIZ`, `Student_ID -> MASTER_STUDENT`. `Submitted_Answers_JSON` contains only selected A–D options, never answer keys. It is retained only through the review/safe-cleanup boundary, then physically deleted with the disposable attempt row.

### `QUIZ_RESULT` — permanent retained canonical summary

Business ID: deterministic `Result_ID = hash(Attempt_ID)`.

```text
Result_ID, Quiz_ID, Quiz_Title, Attempt_ID, Student_ID, Student_Name, Class_ID, Teacher_ID, Raw_Score, Maximum_Score, Normalized_Score, Started_At, Completed_At, Created_At
```

This row is permanent/retained by quiz cleanup. `Quiz_Title`, student display-name snapshot, class and teacher context make it readable after source content is physically deleted. It contains no `Correct_Option`, correctness map, or detailed answers. Leaderboards read this sheet only.

No leaderboard sheet is proposed.

## Forensic reuse

- Authentication and role gates: Laravel auth plus the existing `role` middleware.
- Teacher identity: authenticated `User_ID -> MASTER_TEACHER.Teacher_ID`, active only, fail closed.
- Teacher class scope: active `MASTER_SCHEDULE.Teacher_ID -> Class_ID`, intersected with active `MASTER_CLASS`.
- Student identity: authenticated `User_ID -> MASTER_STUDENT.Student_ID + current Class_ID`, active only, fail closed.
- Persistence: existing repository interfaces plus `BaseSheetRepository` cache, request-level in-memory rows, retry, primary-key verification, and ambiguity reconciliation.
- Concurrency: existing cache locks with authoritative reads inside the lock.
- Physical deletion: existing `hardDeleteMany`, which re-reads, re-resolves exact IDs, skips ambiguous duplicate keys, and deletes bottom-to-top.
- Clock/scheduler: Carbon in `Asia/Jakarta`; existing Laravel Scheduler and existing VPS `schedule:run`.

## Read-only performance baseline

No production requests or live Google API calls were executed, so no latency figure is claimed. Existing `BaseSheetRepository` already logs per-sheet read duration and cache hit/miss; those logs are the approved source for a future live before/after comparison.

Static route tracing found these cold-path sheet families (optional/failure-isolated reads included):

| Route/workspace | Existing bulk-read families observed |
|---|---|
| Student Dashboard | student, announcement, score, schedule, attendance, invoice, payment, attendance request, activity, notification |
| Teacher Dashboard | teacher, schedule, attendance, assessment, score, student, class, employee/payroll, activity, notification |
| Student Notification Center | notification with user/role targeting |
| Student Billing | student, invoice, payment plus education-fee reference data |
| Teacher Workspace | teacher scope plus page-specific schedule/class/student/attendance/score data |
| Attendance landing/workspace | identity, schedule/class, student, attendance/request data |

The existing repositories already collapse repeated reads of the same repository instance through `inMemoryRows` and shared cache. Without trustworthy live timing evidence, no unrelated cache, Finance, Attendance, Payroll, Academic Score, or dashboard behavior was changed.

## Proven quiz-path hardening and before/after evidence

The reusable general `TeacherScopeResolver` is intentionally broad: resolving a teacher scope loads teacher, schedule, class, student, class-enrollment, and assessment datasets because its academic consumers require them. Reusing it for every Quiz authorization would fetch student/enrollment/assessment data that Quiz class authorization does not use.

The dedicated `QuizScopeService` reduces a cold teacher Quiz authorization from six bulk repository reads in the broad path to exactly three relevant bulk reads (`MASTER_TEACHER`, `MASTER_SCHEDULE`, `MASTER_CLASS`). `H877QuizScopeTest` enforces that `MASTER_STUDENT` is not read on the teacher path. Student Quiz identity is one `MASTER_STUDENT` bulk read. This is call-count evidence, not invented wall-clock timing.

Additional performance contracts:

- No per-second HTTP request; the countdown is local display only.
- No per-option Sheets write; one controlled final submission stores selected answers.
- Each service operation bulk-loads a Quiz sheet at most once unless a fresh authoritative recheck is security-critical.
- Student/teacher list aggregation keys bulk collections rather than issuing per-row reads.
- Leaderboard reads `QUIZ_RESULT` only and filters `Class_ID + [Period_Start, Period_End)`.
- Dashboard code was not coupled to Question/Attempt sheets.
- Cleanup is bounded (default 50 quizzes), daily, lock-protected, and removes closed-period content.
- Cache added: **NO**. Existing repository cache/memoization was reused; existing write invalidation remains authoritative.

## Non-ACID limitation

Google Sheets is not a transactional datastore. Cross-sheet writes cannot be made atomically. The implementation mitigates this with deterministic attempt/result IDs, process locks, fresh authoritative rechecks, duplicate-key rejection, and post-ambiguity primary-key verification. Result creation occurs before an attempt is marked submitted, so a retry can recover the canonical result without duplicating it. Cleanup finalizes missing expired-attempt summaries before deleting source content.
